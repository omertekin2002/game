## M05 · Story systems: dialogue, scenes, items, quests and Hoot's Field Notes

**Goal.** ENGINE F13-F16, a scene-script runner and "Ask the Tree". After M05 every line, scene, item and quest of
the 100-hour story is written as data in tables, picked by the condition language of S-025, and listed in a journal.

an item or a quest.

**Vision roadmap item.** **Story systems: dialogue, scenes, items, quests and Hoot's Field Notes** `[agent-feasible]`.

**Entry criteria.** **Filed directly after M02** (INDEX §1.8): M02 closed, and S-024 (save v8: `realm`, `items`,
`quests`, `abilities`, `travel`, `bestiary`, `dungeons` containers) and S-025 (`js/cond.js` and the content lint

`test:playthrough` and in-page suites). M01-M02 shipped the handover cutscene
(`startHandover`, S-005/S-006), `HANDOVER`, `CATCHER_TALK`, `INSTALMENTS` and `MEMORY_LINES` tables in `js/data.js`.

**Exit criteria.**
- `js/text/`, `js/dialogue.js`, `js/scenes.js`, `js/items.js`, `js/quests.js` and `js/hud/journal.js` exist, each
  with unit tests; the content lint runs in CI.

- The three handovers run as scene scripts.
- The `tool` (T, D-pad up) and `journal` (L) actions exist and are rebindable.
- `test:playthrough` and `test:opening` are unchanged; every CI job is green.

**What the player can do at the end.** Open **Hoot's Field Notes** with `L`, from the pause menu, or (pad) from the
map card's tab. The Quests tab lists "The Sneeze" and the two errands with their current step. The Items tab shows
potions, the sword and any Starseed carried. The Lore tab lists Shellby's myth instalments heard, the four keepsakes
found and the handover scenes, which replay. **Ask the Tree** on any quest gives a nudge, then the plain answer, in
Shellby's voice.

**Playtime added.** 0 h (quality of life). Cumulative 4.0 h.

**Save plan.** None. M05 stores everything in v8 containers: `S.flags` (`seen:*`, `scene:*`, `track`, `equip`),

### S-032a · feat: text tables and t() with a content lint

Milestone M05 · Depends on: S-025 · Size: M · Save: none · Flag: none · Bible: [../bible/systems.md#dialogue](../bible/systems.md#dialogue), [../bible/charter.md#tokens](../bible/charter.md#tokens), [../bible/charter.md#line-length](../bible/charter.md#line-length), [../bible/charter.md#reserved-markers](../bible/charter.md#reserved-markers)

#### Why

A 100-hour story has thousands of lines keyed to flags, counts, places and times. Today every line lives inside
`lines(S)` functions in `js/data.js`, written as `if` chains. This step adds text tables: every string by id, read
through `t(id, vars)`, so the lint can check length, tokens and markers in one place. Nothing reads the tables yet,
so nothing changes for players. ENGINE F13, first half (S-032b adds the dialogue picker).
Roadmap: `docs/roadmap/INDEX.md` S-032 (M05 **Story systems: dialogue, scenes, items, quests and Hoot's Field
Notes**), split into S-032a and S-032b in this file's [Index changes](#index-changes).

#### What

1. **`js/text/tokens.js`** (pure, no imports). Exports:
   - `KEY_TOKENS`: `['move', 'look', 'attack', 'jump', 'dash', 'sprint', 'interact', 'potion', 'view', 'shoulder',
     'lock', 'map', 'pause', 'zoom', 'roll', 'lockon', 'use', 'swing', 'hop', 'camera', 'ok', 'back', 'tabPrev',
     'tabNext']`. These are the tokens `js/hud/keys.js` formats today (its header comment and `ALIAS`). S-035 appends
     `tool` and S-037a appends `journal`.
   - `TEXT_VARS`: `['n', 'total', 'left', 'lit', 'title', 'name', 'gems', 'boss']` ([R15](#reconciliations)).
   - `TEXT_PREFIXES`: the realm shorts of systems `#dialogue` (`home`, `cc`, `pw`, `aw`, `tm`, `rd`, `gw`, `ke`, `sg`,
     `dh`, `sm`, `cr`, `rm`, `mm`, `nt`, `mg`), plus `qt` (quest titles and steps), `ht` (hints), `qj` (journal
     entries), `ui`, `hoot` (margin notes), `lore`, `side`, `item`, `best` (bestiary).
   - `TEXT_ID = /^[a-z][a-z0-9]*(\.[A-Za-z0-9_-]+){1,6}$/`.
2. **`js/text/index.js`** (pure). Exports:
   - `addText(table)`: merges `{ id: 'text' }` into the global map. A duplicate id with different text throws (the
     lint catches it first).
   - `t(id, vars)`: returns the text with each `{name}` replaced when `vars` has that own key (numbers are
     `String(n)`). Key tokens stay untouched for `fmtKeys`. A missing id returns the id itself and warns once per id
     when `?debug` is on. It never throws.
   - `has(id)`, `allText()` (for the lint), and `loadText(short)`: a dynamic `import('./en/' + short + '.js')` that
     calls `addText`. It is used by later realm steps, called in `RealmManager.enter` step 5.
   - **Pages build rule:** no string or comment in these files may contain the characters `from '` or `from "`,
     because `tools/build-pages.mjs` rewrites imports by regex. The lint checks every text value for it.
3. **Core tables**, statically imported by `js/text/index.js`: `js/text/en/home.js`, `ui.js`, `quests.js`,
   `items.js` and `lore.js`. Each is `export default { }` with the comment `// text ids: <prefix>.*`. They are empty
   in this PR except `ui.js`, which gets the one test string `'ui.test.dialogue': 'Hoo! This line came from a table.'`
   (kept for the in-page test).
4. **Content lint, text rules** (`tests/content.test.js`, extend; rules 7a-7e):
   - 7a. Every text id matches `TEXT_ID` and starts with a `TEXT_PREFIXES` entry; there are no duplicate ids across
     tables.
   - 7b. Every text is at most 220 characters, counting each `{token}` as 8 characters (charter decision 7).
   - 7c. Every `{x}` in a text is in `KEY_TOKENS` or `TEXT_VARS`.
   - 7d. No text contains `from '`, `from "` or the single-character ellipsis `…`.
   - 7e. `~` appears only in ids containing `.miso.`, and `!!` only in ids containing `.kinako.`.
5. **Debug hook:** `G.debug.text(id, vars)` returns `t(...)`.
6. **Pages build check:** run `node tools/build-pages.mjs` and confirm `dist/js/text/index.js` still imports
   `./en/home.js` etc. unchanged (the import rewrite must not touch the tables).

#### Assets

None.

#### Acceptance criteria

- `t()` fills variables, leaves key tokens for `fmtKeys`, returns the id for a missing id without throwing, and warns
  once per missing id under `?debug` (unit-tested in `tests/text.test.js`).
- `addText` throws on a duplicate id with different text; `loadText('home')` resolves and `has('ui.test.dialogue')`
  is true afterwards.

### S-032b · feat: data-driven dialogue with a fallback to lines(S)

Milestone M05 · Depends on: S-032a, S-025 · Size: M · Save: none · Flag: none · Bible: [../bible/systems.md#dialogue](../bible/systems.md#dialogue), [../bible/systems.md#conditions](../bible/systems.md#conditions)

#### Why

With text tables in place (S-032a), this step adds a dialogue picker that chooses an entry by priority from data,
the condition atoms Act I's lines need, and the hook in `talkTo`. An NPC without entries keeps its shipped
`lines(S)`, so nothing changes for players. ENGINE F13, second half. Part of **Story systems: dialogue, scenes,
items, quests and Hoot's Field Notes**.

#### What

1. **`js/dialogue.js`** (pure). Exports:
   - `PRI = { SCENE: 100, MAIN: 80, COUNT: 60, SIDE: 40, MEMORY: 30, PLACE: 20, IDLE: 10 }`.
   - `addDialogue(entries)` and `entriesFor(npc)`. Entry shape:

     ```js
     { id: 'home.hoot.calmed', npc: 'hoot',
       when: 'boss:woods',                 // cond.js condition (string, array, {any:[...]}, or null)
       lines: ['home.npc.hoot.calmed.1',   // text ids, one dialogue box each
               { t: 'home.npc.hoot.paper.2', when: 'rematch:woods' }],   // a line with its own condition
       vars: ['seedsLeft'],                // named VARS providers (below), optional
       frame: 'default',                   // dialogue frame, optional
       set: ['set:met:hoot'],              // effects applied after the last box, optional
       once: false,                        // true: after showing, apply set:seen:<id>; blocked while seen
       prepend: false,                     // true: shown before the main entry's lines (count beats, memory lines)
       append: false,                      // true: shown after the main entry's lines
       priority: 20,                       // inside a PRI band
       port: false }                       // true for lines ported word for word from lines(S) (S-033)
     ```
   - `pick(npcId, S, ctx = {})` returns `{ main, pre, post, lines, vars }` or `null`. `main` is the highest-priority
     entry with neither `prepend` nor `append` whose `when` holds and that is not `once`-seen (ties: first in table
     order). `pre` is the highest-priority `prepend` entry that holds (at most one); `post` is the highest-priority
     `append` entry that holds (at most one). `lines` is the flattened list of text ids (pre, main, post), each line
     kept only if its own `when` holds. `ctx` is `{ realm, region, hour, only }`. With `only: 'port'`, only `port`
     entries are considered (used by S-033's replay test). Idle entries (`idle: true`, `lines: [[...], [...]]`) use
     the set at `Math.floor(S.playTime / 480) % lines.length`, so the set changes once per game day, never at random.
   - `talkLines(npcId, S, ctx)`: `pick` resolved through `t(id, vars)` to strings, or `null`.
   - `afterTalk(picked, S)`: for `pre`, `main` and `post`, applies `set` effects with `cond.apply` and, for `once`
     entries, `set:seen:<entry id>`. Returns the events `apply` returns.
   - `VARS`: named providers `(S) => value`, each pure, over the shipped helpers in `js/data.js`. `seedsLeft`
     (3 − placed), `seedsPlaced`, `paradeLit`, `paradeTotal` (4), `shellsFound`, `shellsTotal` (5). An entry's
     `vars: ['seedsLeft']` fills `{left}`, and so on. Mapping: `seedsLeft → left`, `seedsPlaced → n`,
     `paradeLit → lit`, `paradeTotal → total`, `shellsFound → n`, `shellsTotal → total`.
2. **New condition atoms in `js/cond.js`**, each with a unit test (pure readers of the v6 fields and the shipped
   helpers `progress`, `errands`, `shop`, `rematch`, `secrets`):
   - **General negation:** `!` before any atom negates it, not only before `flag:` and `item:`.
   - `carried>=<n>` (Starseeds carried, `S.seeds[x] === 1`), `introDone`, `chest:<id>` (`S.chests[id]` truthy),
     `rematch:<id>`, `rematches>=<n>`, `errand:<id>=<0|1|2>`, `errandItems:<id>>=<n>` (`errands.found`),
     `plushies>=<n>` (`shop.plushies`), `plushStock>=<n>` (`shop.inStock`) and `shopOut` (`shop.boughtOut`).
   - Register the new atoms in the lint's known-atom list.
3. **Wiring** (`js/interact.js` `talkTo(npc)`):
   - If `npc.def.talk` is set (a realm short, for example `'home'`), call
     `pick(npc.id, S, { realm: W.realm ? W.realm.id : 'home', region: <current region id>, hour: S.tod * 24 })`.
     If it returns lines, show them through `ui.say(lines, { name, portrait, frame })` and call `afterTalk` in
     `onDone`, before the shop or errand code that runs today.
   - Otherwise keep `npc.def.lines(S)` exactly as today. No NPC gets `talk` in this PR, so every villager keeps
     `lines(S)` (S-033 ports them).
   - `ui.say` accepts `o.frame`. A frame other than `'default'` adds the class `frame-<name>` to `#dialogue`; this PR
     ships no frame CSS.
4. **Content lint, dialogue rule** (`tests/content.test.js`, extend; rule 7f): every dialogue entry's line ids
   exist (`has(id)`), its `when` and line conditions parse with known atoms, its `set` effects name registered flags,
   `priority` is inside `PRI`'s 10-100 range, and its `vars` names exist in `VARS`.
5. **Debug hook:** `G.debug.dialogue.pick(npcId)` returns `{ main, pre, post, lines }` ids for the current save.
6. **New in-page suite `story`** (`js/debug/tests/story.js`, registered in `js/debug/tests.js`, CI matrix entry
   `story`): the test "a table entry outranks lines(S)". It calls `addDialogue([{ id: 'test.hoot', npc: 'hoot', when:

### S-049 · feat: a dungeon text-map compiler and lock-and-key solver

Milestone M07 · Depends on: none · Size: M · Save: none · Flag: none · Bible: [../bible/dungeons.md#format](../bible/dungeons.md#format), [../bible/dungeons.md#legend](../bible/dungeons.md#legend), [../bible/dungeons.md#reach](../bible/dungeons.md#reach), [../bible/dungeons.md#solver](../bible/dungeons.md#solver), [../bible/dungeons.md#entities](../bible/dungeons.md#entities)

#### Why

Fifteen dungeons and 24 Hollows, 172 rooms in all, are written as ASCII maps in the bible. An implementer must know a
map works (exit and boss door reachable, every chest openable, no soft-lock) before a browser ever loads it. This step
adds the pure compiler and the state-search solver, both in `bun test`, with exact error messages. ENGINE F21. Part of
**Abilities and the dungeon engine**.

#### What

1. **`js/realms/dungeon-compile.js`** (pure; no Three.js, DOM or storage). Exports `compile(data)` and `solve(compiled,
   opts)`, plus the shared rule helpers `canPush`, `reachStep` and `doorOpen` (S-053 uses the same functions at
   runtime).
   - **Input:** the format of dungeons `#format` (`levels`, `rooms`, `legend`, `entities`, `chests`, `spawns`, `light`,
     `parent`, `door`, `exit`, `needsOnEntry`, `solution`).
   - **Tiles** are 2 m: tile (col, row) has its centre at world `(2·col + 1 + 8 + at.x·2, 2·row + 1 + 8 + at.z·2)`
     minus half the realm size, so the realm is centred on 0.
   - **Heights:** `.` 0; digit d → d × 0.3 m; `_` → −4 (pit, `respawn` flag); `~` → floor −4 with a water plane at
     −0.3; `w` → −0.3 with the water plane at −0.1 (`wade`); `=` → a bridge deck at 0 over −4; entity tiles take the
     most common floor height of their 8 neighbours, ties upward (rule 8); doors take the height of the floors they
     join.
   - **Output:**

     ```js
     { id, size,            // realm grid metres: extent + 16, rounded up to even, clamped 48..192
       cells: { n, H: Float32Array (1 m), walk: Uint8Array, tile: Int16Array (tile index per cell) },
       rooms: [{ id, name, level, box, cells: [tileIdx], dark, ceil, centre: {x, z} }],
       walls: [{ x, z, hx, hz, h }],          // greedy rectangle merge of '#' runs; h = 3.2 + highest floor beside
       ceilings: [{ room, x, z, hx, hz, y }], // one `over` box per room at its ceil
       ents: { '<room>:<glyph><n>': { glyph, kind, col, row, x, z, y, room, ...entities[id] } },
       spawns: { entry: { x, z, facing } }, exits: [{ id, x, z, to }], warps: [{ id, pair }],
       lamps: [{ x, y, z, id }],              // 't' torches and 'l' lanterns (lit state at runtime)
       waves: { <room>: [{ wave, species, n, at }] }, warnings: [] }
     ```

   - **Rooms by flood fill** (rule 6): 4-connected non-wall, non-door, non-space tiles. A `rooms[].box` that does not
     match its region fails with `<id>: room <rid> box [c,r,w,h] does not match its tiles (found [..])`.
   - **Entity ids** (rule 5): `<room>:<glyph><n>`, counted in reading order per room. A door in a horizontal wall
     belongs to the room above, in a vertical wall to the room on the left.
   - A merged wall count over 300 is a warning; a grid over 192 m fails.
2. **The solver** (dungeons `#solver`, reach rules `#reach`):
   - **State:** reachable region, small keys held, Root Key, each switch's on/off, the lanterns lit, block positions,
     doors opened for good, chests opened, and tools (from `needsOnEntry` plus treasure chests opened).
   - **Moves:**
     - walk: one digit up a tile, a hop up two digits, a one-tile hop over `_` or `~`, any drop;
     - doors: pass a `D` whose condition holds; an `O` always;
     - small keys: pick up a `k` whose condition holds (`always`, `plate:<id>` while held, `clear`);
     - locked doors: open an `L` (uses one key), and a `B` with the Root Key;
     - chests: open them (`$` adds its tool);
     - switches: toggle one (from an adjacent tile, or within a sword's reach of 1 tile);
     - lanterns: kindle an `l` (needs `lantern`);
     - blocks: push a block (`canPush`: Pip on the opposite side, the target tile is floor of the same height, free of
       blocks, pillars, chests and closed doors, never `_ ~ w =`);
     - lever: pull an `r` (its room's blocks return home);
     - warps: take a `^`;
     - waves: clear a room's waves (always possible with the sword; a wave with a `ghost`-archetype species needs
       `lantern` or a lit room).
   - **Plates:** a `p` is down only under a block, or while Pip stands on it (a `plate:` door does not let Pip through
     while he stands elsewhere); `P` only under a block. Pit-plates (`kind: 'pitplate'`) are boss mechanics and never
     hold doors.
   - **Proves:**
     1. the exit and every `B` are reachable from `@`;
     2. every `c & % K $ H + *` can be opened;
     3. no soft-lock: from every reachable state, the exit and every unopened required target are still reachable;
     4. keys: the number of keys reachable before each `L` is at least the number of `L` that must open before it;
     5. `data.solution`, a list of `['goto' | 'take' | 'open' | 'unlock' | 'hit' | 'kindle' | 'push' | 'pull' |
        'warp' | 'clear', entityId, dir?]`, replays legally.
   - A state cap of 200,000 fails with `<id>: state space over 200000`.
   - **Messages** (exact formats): `<id>: <ent> (<c>,<r>) unreachable; needs <what>`; `<id>: <ent> (<c>,<r>) needs 1
     small key, 0 reachable before it`; `<id>: after <ent> pushed <dir> to (<c>,<r>), <target> (<c>,<r>) can no
     longer be reached (no reset lever in <room>)`; `<id>: solution step <n> (<action> <ent>) is not legal here`.

### S-052 · feat: puzzle entities I: doors, keys, locked and boss doors, plates, map and Chime Stone

Milestone M07 · Depends on: S-051, S-050, S-037b · Size: M · Save: none · Flag: none · Bible: [../bible/dungeons.md#entities](../bible/dungeons.md#entities), [../bible/dungeons.md#state](../bible/dungeons.md#state), [../bible/dungeons.md#rules](../bible/dungeons.md#rules), [../bible/charter.md#verbs-new](../bible/charter.md#verbs-new)

#### Why

Doors that open on a condition, keys that unlock them, a Root Key for the boss door, plates, chests and the map and

#### What

1. **`js/dungeon-mod.js`** (module; `onWorld` builds from `W.dungeon`; `afterStep` ticks):
   - **Doors `D`:** the condition is one of `plate:<id>`, `plates:[ids]`, `switch:<id>`, `clear`, `lit:[ids]`,
     `boss`, `flag:<key>` or `always`, evaluated by S-049's `doorOpen(state, ent)`. Open means the collider is
     `active = false` and the leaf slides up 0.6 s (the vine-gate animation of `fight.js buildVineWalls`), with
     `sfx('door_open')`. `clear`, `lit`, `boss` and `flag` doors stay open for good (`S.dungeons[id].open[ent] =
     true`). `plate` and `switch` doors follow their trigger live.
   - **Locked doors `L`:** an interactable `lock`. With `keys > 0`: `[E] Unlock · Door` (charter verb Unlock, added to
     `interact.js`'s verb set and the lint's verb list) uses one key; the plate pops off and rolls 1 m; open for good.
     Without a key: `[E] Look · Locked door`, which says "It needs a small key." (`ui.dungeon.needkey`).
   - **Boss door `B`:** `[E] Unlock · Big door` with `bigKey`; the spiral turns 360° in 1.2 s; the key is kept.
     Without it: `[E] Look · Big door`, which says "A big spiral lock. It needs the Root Key." (`ui.dungeon.needbig`).
   - **Small key `k`:** shown while its condition holds (default `always`; `plate:` while held; `clear` once the room's
     last wave has poofed). Picked up by walking within 0.9 m: `keys + 1` and the item-get beat "You got a small key!"
     / "It opens one locked door in this dungeon." (`ui.dungeon.get.key.1`, `.2`).
   - **Chests** (reusing `int_chest_small` / `int_chest_big` and the shipped `openChest` beat, `[E] Open · Chest`):
     - `c`: 40 gems ("+40 gems!");
     - `&`: the map ("You got the dungeon map!" / "Every room is on it now.");
     - `%`: the Chime Stone ("You got the Chime Stone! It hums near treasure." / "Treasure shows as little stars on the map.");
     - `K`: the Root Key ("You got the Root Key!" / "It opens the big spiral door.");

     the dungeon realm), with at most 4 alive per room. While a wave is live, the room's `clear` doors (and the door Pip
     came in through, when its entity says `seal: true`) are sealed with glowing vines (the shipped look). Enemies
     never leave their room (a `canGo` clamp to the room's tiles). The last poof opens `clear` doors for good.
   - **Rooms visited:** `S.dungeons[id].rooms[room] = true` on entry.

#### Why

Switches and blocks are the most common puzzle in the 172 rooms. Their runtime must agree with the solver tile for
tile, or a map the solver passed could soft-lock in play. This step implements both through the solver's own rule
functions, plus the reset lever, with block positions saved. ENGINE F23 part 2. Part of **Abilities and the dungeon
engine**.

#### What

1. **Crystal switch `s`:**
   - A combat target: `resolveSword` tests switch hurtboxes (a cylinder r 0.4, 0.3-1.2 m up) with the swing volume and
     emits `EV.HIT { kind: 'switch', target }`.
   - Each hit toggles the switch (0.5 s cooldown): blue `#9fdcff` off, gold `#ffd36b` on, a chime up or down.
     `state['<ent>'] = true / false` is saved.
   - Doors with `switch:<id>` follow it live. A switch entity with `lights: [ids]` lights those lanterns for good on
     its first "on" (`lit[...] = true`), with a gold vein (a 0.6 s emissive line decal) drawn along the floor from the
     switch to each lantern (dungeons R7).
   - Beam and ember hits toggle it too once those tools exist (their steps emit `EV.HIT kind 'switch'`).
2. **Push-block `b`** (`int_block`):
   - A dynamic box collider 1.9 m. When Pip walks into a face with his intent within 30° of the face normal, for
     0.35 s, it slides one tile in 0.3 s if `canPush` (S-049, the same function the solver uses) allows it, with
     `sfx('block_slide')` and dust.
   - It is not pushable while a wave is live in the room (`canPush` receives `waveLive`).
   - Its tile is saved in `blocks['<ent>'] = [c, r]` after each push. On load it is placed at the saved tile.
   - Plates under blocks update at once.
3. **Reset lever `r`** (`int_lever`): `[E] Use · Lever` pulls the arm (0.3 s). Every block of its room fades out 0.3 s,
   moves to its start tile and fades in 0.3 s; its saved positions are deleted.
4. **Solver agreement test** (`tests/dungeon-compile.test.js`): for `fx_blocks`, `fx_corner` and `sandbox_dungeon`,
   1,000 random sequences of pushes from `mulberry32(7)` applied with `canPush` give the same reachable block tiles as
   the solver's state search (the runtime and the solver share one function; this checks the bookkeeping around it).
5. **`sandbox_dungeon`** is now fully playable: switch `r1:s1` → `r1:D1` → r2; push `r2:b1` S × 2 → `r2:P1` →
   `r2:D1` opens; the lever resets.
6. **Debug:** `G.debug.dungeon.push(entId, dir)` (runs the real push), `.hit(entId)`.

#### Assets
